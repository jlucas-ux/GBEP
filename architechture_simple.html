Step 4 — How the data download works (and why it's unusual)

The ESRI website wraps our HTML files in a security container (called a sandbox) that normally blocks file downloads. We worked around this using a standard browser feature:

1
User clicks Download
Inside the ESRI sandbox — file download is blocked here
→
2
New tab opens
A new browser tab opens — this one is outside the sandbox restriction
→
3
File is built
The new tab builds the CSV or GeoJSON from the current filtered data
→
4
Download completes
The file downloads normally. The tab can be closed.

⚠️ If a user has popup blocking enabled in their browser, the new tab may be blocked. The download will still show a copy-paste modal as a fallback. This is an ESRI platform limitation, not a bug in our code.

The public repo + private credentials paradox — and how we solved it
⚠️ The problem
GitHub Pages requires a public repository
Free GitHub Pages hosting only works if the repository is public — meaning anyone on the internet can view the code. This is non-negotiable without a paid GitHub plan.

But some of the HTML files are password-protected. Putting passwords directly in the code would expose them to everyone.
✅ The solution
GitHub Secrets + GitHub Actions
Credentials (usernames, passwords, protected HTML) are stored in GitHub Secrets — an encrypted vault built into GitHub that is never visible in the code, never logged, and never accessible to anyone viewing the repository.

A GitHub Actions workflow injects those secrets into the files automatically on each deploy.
How it works step by step
1
Developer pushes code
A code change is committed and pushed to GitHub. The repo is public — but contains no passwords.
→
2
GitHub Actions runs
An automated workflow triggers. It runs in a private, secure environment that can access GitHub Secrets.
→
3
Secrets injected
The workflow reads the encrypted username, password, and protected HTML from the Secrets vault and inserts them into the files.
→
4
Live site updated
The completed files (with credentials embedded) are deployed to GitHub Pages. Credentials exist only in the live files — never in the repo code.
What is and isn't visible
Item Public repo
(anyone can see)		 GitHub Secrets
(encrypted, hidden)		 Notes
Chart HTML files ✅ — index.html, browse_projects.html, etc. — public code, no credentials
Password-protected HTML 🚫 ✅ Stored encrypted in Secrets vault; injected by Actions at deploy time
Username & password 🚫 ✅ Never in the code. Only ever exist as encrypted secrets and in the deployed live files.
ArcGIS service URL ⚠️ — Visible in code — intentional. Service is public read-only; no risk in exposure.
GitHub Actions workflow ✅ — The workflow logic is public, but it only reads secrets by name — values never appear in logs
Commit history ✅ — Full history visible — safe because credentials were never committed in the first place
Bottom line for a maintainer: The repository being public does not create a security risk. All sensitive credentials live exclusively in GitHub's encrypted Secrets vault. To update a password or protected file, you change the Secret in GitHub — not the code. Go to: GitHub repo → Settings → Secrets and variables → Actions.
Security at a glance

🔒 Security considerations

✅
Read-only data access The public dashboard can only read project records. No one can add, edit, or delete data through the website.
✅
No passwords in code The ArcGIS data service is intentionally public. No login credentials are embedded anywhere in the HTML files.
✅
Always up to date Data is fetched live on every page load. New Survey123 entries appear immediately with no manual steps.
✅
No server or database of our own Everything runs in the user's browser. We don't store, log, or process any data on our end.
